# Managing Change

## Why Software Changes
- Business requirements evolve.
- User needs change.
- Technology advances.
- Bugs are discovered.
- Performance requirements grow.
- Regulations change.

## Core Principle
- The only certainty in software is that it will change.

## Stable vs Unstable Parts
- Stable parts represent core domain concepts and change infrequently.
- Unstable parts evolve frequently and should be isolated from the rest of the system.

## Anticipating Change
- Design for changes that are likely based on current knowledge.
- Do not try to predict every possible future requirement.

## Designing for Extension
- Structure software so new behaviour can be added with minimal modification to existing code.

## Over-Engineering
- Adding unnecessary flexibility for hypothetical future requirements.
- Good design balances extensibility with simplicity.

## Mental Model
- Good software design does not prevent change.
- It localises change so that modifications affect as few modules as possible.
