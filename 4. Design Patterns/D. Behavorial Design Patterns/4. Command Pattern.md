# Command Pattern

## Problem
- The sender should not need to know how an action is performed.
- Requests may need to be queued, logged, retried, scheduled, or undone.

## Core Idea
- Encapsulate a request as an object.
- Separate the object that invokes the action from the object that performs it.

## Participants
- Invoker: Triggers the command.
- Command: Represents the request.
- Receiver: Performs the actual work.

## Recognition Questions
- Is an operation represented as an object?
- Do requests need to be queued or replayed?
- Does the invoker depend only on a command interface?

## SOLID Principles
- SRP: Invoker, command, and receiver each have distinct responsibilities.
- OCP: Add new commands without modifying the invoker.
- DIP: Invoker depends on the command abstraction.
- LSP: Any command implementation can be substituted.

## Comparison
- Strategy: Chooses one algorithm.
- Observer: Broadcasts events to many listeners.
- Command: Packages an action as an object.

## Key Insight
- Command turns "something to do" into a first-class object that can be stored, passed around, delayed, or replayed.
