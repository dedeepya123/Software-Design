# Observer Pattern

## Problem
- One object's state changes, and multiple other objects need to react.
- Directly calling every dependent object creates tight coupling.

## Core Idea
- Maintain a list of observers.
- Notify all registered observers whenever an important event occurs.
- The subject doesn't need to know what each observer does.

## Recognition Questions
- Does one event trigger many independent actions?
- Can observers be added or removed at runtime?
- Does the subject depend only on an observer interface?

## Participants
- Subject (Publisher): Generates events and notifies observers.
- Observer (Subscriber): Reacts to notifications.

## SOLID Principles
- SRP: Subject manages its own state; observers manage their own reactions.
- OCP: Add new observers without modifying the subject.
- DIP: Subject depends on the observer abstraction.
- LSP: Any observer implementation can be substituted.

## Comparison
- Strategy: Choose one algorithm.
- Observer: Notify many listeners.

## Key Insight
- Observer decouples the producer of an event from the consumers of that event.
