# Facade Pattern

## Problem
- A subsystem contains many collaborating classes.
- Clients must understand too much internal complexity to perform common tasks.

## Core Idea
- Introduce a facade that provides a simple, high-level interface to the subsystem.
- The facade coordinates the subsystem while hiding unnecessary details.

## Recognition Questions
- Does one class mainly orchestrate several subsystem classes?
- Does it expose a simpler API for common workflows?
- Does it mostly delegate work instead of implementing the subsystem itself?

## SOLID Principles
- SRP: The facade is responsible for coordination; subsystem classes keep their own responsibilities.
- DIP: Clients depend on the facade rather than many subsystem classes.
- OCP: Internal subsystem changes can often be absorbed inside the facade without affecting clients.

## Comparison
- Adapter: Makes incompatible interfaces work together.
- Decorator: Adds behaviour to an existing object.
- Facade: Simplifies access to a complex subsystem.

## Key Insight
- Facade doesn't reduce the subsystem's complexity. It reduces the complexity exposed to the client.
