# Creational Patterns Summary

## Core Principle
- Every creational pattern answers a different object-creation question.

## Decision Guide
1. Should only one instance exist? → Singleton
2. Should object creation be separated from the client? → Factory Method
3. Do I need a family of compatible objects? → Abstract Factory
4. Is one object complex to construct? → Builder
5. Do I already have a similar object that I can copy? → Prototype

## Recognition Strategy
- Focus on the design problem, not the implementation syntax.
- Patterns emerge naturally as systems become more complex.

## Relationship to SOLID
- Factory Method → Supports DIP by hiding concrete implementations.
- Builder → Supports SRP by separating construction from the product.
- Abstract Factory → Supports OCP by allowing new product families.
- Singleton → Useful for unique shared resources, but should be applied carefully.
- Prototype → Reuses existing state instead of repeating expensive initialisation.

## Key Insight
- Patterns are solutions to recurring design problems.
- Start with the problem, ask the right questions, and the appropriate pattern usually becomes clear.

``` text

CREATIONAL PATTERNS

Object Creation

│
├── Only one object should exist?
│       ↓
│   Singleton
│
├── Client shouldn't create objects?
│       ↓
│   Factory Method
│
├── Need compatible families?
│       ↓
│   Abstract Factory
│
├── One object is difficult to construct?
│       ↓
│   Builder
│
└── Existing object is almost correct?
        ↓
    Prototype
```
## Example 
``` text
LLM Serving System

│
├── One GPU Resource Manager
│      → Singleton
│
├── Load Gemma, Llama or Phi models
│      → Factory Method
│
├── CPU Backend / GPU Backend / TPU Backend
│      → Abstract Factory
│
├── Build Inference Engine
│      → Builder
│
└── Duplicate Experiment Configurations
       → Prototype
```
